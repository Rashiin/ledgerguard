# Known-risk register

This register lists the risks that remain after the mitigations in place. It feeds the security self-assessment. Each row gives the risk, what limits it today and what is left over.

| ID | Risk | Mitigation in place | Residual |
|---|---|---|---|
| R-01 | Provisioning writes the database outside the Executor. Migrations and the seeder need to. | They run from `scripts/seed.py` as a build step before the app starts. A test starts the real app in a clean interpreter and proves that no provisioning, seeder or Alembic module is loaded. Another test proves engines are created in four named files only. | Anyone who can run the build scripts can rewrite the ledger. This is a documented build-time exception to the rule that only the Executor writes. The running app has no such path. |
| R-02 | Code inside the application process can read the sealing key. | The seal stops hand-built actions, accidental bypass and edits to stored pending actions. The key file is readable only by its owner and is never committed. | A compromised application process could forge seals. That is out of scope for a single-machine sandbox. |
| R-03 | Someone with file access rewrites the audit log consistently, changing an event and every later hash. | Triggers refuse UPDATE and DELETE. The chain detects any edit that leaves later hashes unchanged. The submission evidence publishes the head hash. | The chain is unkeyed SHA-256, so a consistent rewrite needs file access and no secret. Only a comparison with a head hash recorded elsewhere reveals it. The log is tamper-evident with a published head hash. It is not tamper-proof. |
| R-04 | The seasonal fill in the projection is crude. | Its lines are tagged `SPECULATIVE` and never merged with other classes. Each line cites the invoice it repeats. Every shortfall is also quoted on contracted-only cash. | It applies no growth or trend, and it repeats last year's one-off orders. |
| R-05 | Variable spend with no invoice or obligation row is not projected. Fuel, utilities, insurance and bank fees come to about €4,000 a month. | The omission is documented in fixtures/README.md and in D-005. | The projection is optimistic by about that amount. |
| R-06 | One person can act as both operator and owner. | T2 and T3 need a human approver role. T3 adds a typed confirmation and a cool-off. | There is no authentication and no separation of duties. One person at the keyboard can approve anything that is not blocked. |
| R-07 | The ledger is a sandbox. | There is no bank or payment-provider integration. | Executing a payment changes ledger rows. No money moves. |
| R-08 | The model can propose a bad plan inside an allowed tier, such as answering the wrong question or paying a valid but unintended invoice. | Every figure is recomputed. Payments need T3 approval with a typed confirmation and the receipt in front of the approver. Rules block unsafe outcomes whatever the plan. | The verifier checks safety and arithmetic. It does not judge whether an action was wise or wanted. The human approver remains the control for intent. |
| R-09 | Numbers in the model's prose are found by pattern matching. | Every money-like number must equal a verified figure or it is masked visibly. See D-017. | Amounts written in words, such as "forty thousand", are not detected. |
| R-10 | Rules are only as good as the ledger and the projection. | The data is synthetic and documented. The projection model is published. Every rule states its reason. | Missing or wrong ledger data, such as an unrecorded payable, gives wrong rule results. Nothing reconciles the ledger against a bank. |
| R-11 | Time passes between verification and execution. | Approval re-runs every rule on the current ledger. Handlers re-check what each invoice owes. Each sealed action runs once. | T0 and T1 actions run at once on the snapshot they were verified against. None of them moves money. |
| R-12 | The payroll and tax rules count the order book as cash. | The speculative fill is excluded. The band is configurable, and `contracted` is the stricter setting. | If confirmed orders fail to convert, payroll and tax protection is weaker than the numbers suggest. |
| R-13 | The rule engine has no formal verification. | The rules are small pure functions. Each has a test proving its BLOCK case. The invariants are tested, and coverage of the verifier, rules and Executor is above 94%. | Tests cover chosen cases. They do not prove correctness for every input. |
| R-14 | An inflated recorded receipt raises projected cash. That could relax a cash-dependent rule such as PayrollProtection or TaxReserveFloor for a later payment. | A recorded receipt cannot exceed what the cited invoice still owes, checked at verification and again at execution. Recording a receipt is T2 and needs a person to approve it. | Someone who approves a receipt that never arrived can make a later payment look affordable. Nothing reconciles recorded receipts against a bank feed. |
| R-15 | Stage 4b only knows the materiality conditions it has been told. | The conditions cover a projected shortfall, a block, revenue concentration and, from Phase 5, high-severity alerts. | An omission outside those conditions passes. Adding a condition is a code change, so the list grows only as fast as someone notices a new kind of harm. |
| R-16 | A response can cite a mandatory fact and still frame it badly, for example by calling the shortfall nothing to worry about. | Numbers in the sentence must match the fact, and guarantee language is masked. | The verifier checks figures and citations, not the tone of the sentence around them. |
| R-17 | The materiality check trusts the orchestrator's record of which tools ran. | The model's output cannot set that record. Forecasts, scenarios and financing rankings always count as cash answers. | A bug that drops a tool from the record would weaken stage 4b for that turn. |
| R-18 | The allowlist routes requests with patterns. | A request that matches nothing can only be answered. Every money-moving kind still needs T3 approval with a typed confirmation. | A misroute either narrows what the agent can do, which is visible and safe, or widens it, and then the tiers and rules still apply. A misroute degrades helpfulness, never safety, which is the same claim the design makes about model quality. |
| R-19 | The neutraliser for untrusted text uses patterns and will miss some phrasings. | Untrusted text is also fenced in data tags. The allowlist comes from the owner's words only. The verifier and rules never read the prompt. | An instruction that slips through can still steer what the model proposes, within the allowed kinds and subject to every check. |
| R-20 | The demo replays recorded model output, not live inference. | Recordings are unedited, matched to the exact request, and made with `scripts/record_turn.py` against the shipped model. Anyone with Ollama can record them again. | A judge sees what the model did when it was recorded, not what it does on their machine today. |
